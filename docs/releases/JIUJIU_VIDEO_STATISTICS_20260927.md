# 九九项目公开播放量核验入口

日期：2026-09-27。首轮范围为测试服“九九 IP 号”项目的已接受公开视频；下文“同账号连载补核”记录随后扩展到候选/入围视频的独立发布与验收。不改生产环境，不自动发起付费调用。TikHub 的[抖音 App V3 视频统计接口](https://docs.tikhub.io/186826221e0)用于单次核验最多 2 个精确视频 ID 的点赞、下载、播放和分享统计；详情接口返回的 0 播放仍保留为原始快照，不再把它直接当作真实播放量。

## 输入、输出与边界

- 输入：当前 Windmill 登录用户、项目 ID、1–2 个精确抖音视频 ID；只允许 active 项目的 Owner/Admin 核验本项目 `accepted` 视频。预览只查库；执行还需明确确认，运行期间在 HTTP 前和写快照前再次核验项目权限。脚本只从 Windmill Secret 读取 TikHub Key。
- 接口：`douyin.app.video_statistics`，单次最多 2 个 ID；只读取 `data.statistics_list` 的结果项，必须完整匹配请求 ID、每个 ID 有非负播放数，否则不提升为业务指标。HTTP 200 响应先原样持久留存，随后验证业务字段；即使业务校验失败，已成功外呼的报价仍作为估算列账，实扣另待对账。指标以新来源快照追加，不改视频/账号主数据。迁移 039 仅改变合并展示优先级，使独立统计的播放量优先于旧详情/榜单零值；缺失的其他字段仍取原来源。
- 输出：两个视频的播放量、快照数、新发/缓存调用数、项目运行 ID、基础价格估算；不给页面返回原始 Provider 响应或 Key。项目日账将此任务列为“播放核验”，估算与供应商实扣仍分开。
- 业务验收：真实统计值必须在视频详情、指标时间线、账号页与项目日账回读；要和已保存的旧详情 0 值并列核查。即使取到播放量，也不足以证明内容方案优劣，还需完整审片、同类分层比较及目标受众验证。

## 九九业务解释与仍需验收

这次解决了“两条样本有互动却显示 0 播放、无法计算分母”的数据质量问题，尚不能据两条非同批、不同发布时间和账号基础盘的视频判断哪种角色叙事更优。现有案例核看仍是抽点画面、原声未完整人工核听、机器转写未校正，粉丝/分享来源存在冲突；目标客群 18–35 岁的识别、续看理由和复访数据也不存在。下一道业务门槛是完整音画核看与同一批目标受众的盲测，再把可复用的具体形式假设交给“九九”自己的小规模内容实验验证，而不是从这两条播放数直接下方向结论。
