# 通用内容研究与效果闭环

日期：2026-09-23。九九是首个业务样本，不是系统专用字段或唯一研究对象。本设计是待实现的业务契约；现有 V1 已有采集、证据、L3 和部分人工标注，但没有完整发布/效果回流。多项目与各类账号不靠 `research_subject` 一个字段解决；身份、业务关系、授权与项目权限另见[通用账号关系模型](GENERIC_PROJECT_ACCOUNT_MODEL_V1.md)。

## 通用对象与职责

| 对象 | 最小字段与关系 | 谁维护 | 作用 |
|---|---|---|---|
| `research_subject` | ID、类型、名称、父对象、有效期、事实来源、负责人；类型可为景区、IP、角色、演艺、活动、商品、品牌、账号等 | 业务负责人 | 同一平台可同时研究“渔岛景区”“螭吻九九”“神兽觉醒”“某次演出”，并明确层级，不以关键词当身份 |
| `subject_alias` / `subject_scope` | 别名、正向上下文、排除词、竞品/可比范围、适用平台及规则版本 | 研究员与业务负责人 | 同名词不能直接视为同一个主体；规则可回看、纠错和重新计算 |
| `subject_profile_version` | 目标客群、场景、品牌/叙事约束、可用素材与权利、禁用表述、当前业务事实、核准人和版本；按对象类型扩展字段 | 内容/运营负责人 | 给研究和 L3 一个有版本的目标上下文；“角色关系”只适用于 IP/角色，“价格库存”只适用于商品/活动，不要求所有对象填同一大表 |
| `subject_candidate` | 对象 ID、源视频/账号 ID、相关性 pending/relevant/irrelevant、理由、规则版本、人工修正、证据链接 | 研究员 | 一个视频可同时关联多个对象；原始采集资产不因某对象判无关而删除，全局简报不得混入错误主体 |
| `content_decision` | 目标对象、研究问题、证据、可借鉴机制、适用/不适用条件、采用/观察/否决、负责人、目标指标、观察期 | 内容负责人 | 从外部案例转为可执行且可反驳的假设，不把 L3 文本直接当发布命令 |
| `content_release` | 选题 ID、脚本/素材/审核版本、自有账号和平台作品 ID、发布时间、渠道/投流/活动入口 | 发布负责人 | 把实际发布与研究依据连起来；不代替真正的发布平台或审批流程 |
| `outcome_snapshot` | 对象、作品/活动、指标名、值、单位、观察起止/时区、来源记录和版本、来源报告时间、导入时间、自然/投流/未知、观测/估算/未知、状态与修订版本 | 运营/数据负责人 | 首步拟实现人工汇总导入，唯一键按来源记录和统计维度设计；迟到修订保留 superseded/retracted 历史，不覆盖旧证据；不强制所有业务都用票务转化衡量 |
| `learning_hypothesis` | 假设、支持/反例、适用条件、证据等级、复验次数、状态（待验证/可复用/已失效） | 内容与运营共同维护 | 结果反哺下一轮研究，防止单次高播放固化为“成功公式” |

这些是**建议的逻辑对象，不表示数据库表已存在**。对象类型采用注册的扩展 schema 和校验规则，通用字段保持稳定；IP/角色可加设定版本、角色关系与使用权，商品可加可售期/价库，均非所有对象必填。首批模板可为“IP 叙事”“景区体验”“活动转化”，不在各业务里复制一套采集器、L3、权限和成本账。

这相对原 V1 范围是业务验收提案：先做人工汇总回填以验证是否有用；发布后账号指标的**自动**授权回流仍按 [V2 规划](SELF_ACCOUNT_FEEDBACK_V2.md)推进，不能把提案当成已经部署的能力。

## 通用流程与接口边界

`业务目标/研究对象 → 有作用域的发现 → 相关性/证据审核 → 决策卡 → 人工创作与发布 → 自有结果回填 → 对照复盘 → 更新经验`。

1. 发现层仍复用现有平台 Provider、Canonical 视频/账号、指标快照和调用账本；先通过数据库迁移和 API/页面兼容，把当前仅支持抖音三种来源且无 `subject_id` 的 `research_brief` 接到通用主体。研究素材与对象是多对多。先做相关性门控，再把候选推给该对象的简报、评分或 L3，不能由全局视频库直接推出特定业务结论。
2. 分析层输入目标对象的**核准版本摘要**、可用证据和版本指纹；区分观察事实、模型假设和人工判断。不同主体的 L3 结果不能共用同一条无主体约束的 `ip_fit`。现有 L3 严格使用 `l3-research-v1.0.0`、固定七段输出和人工审核指纹；因此须另立版本化 `subject_fit` 契约，把 `subject_id/profile_version/relevance_decision` 绑定证据、审核指纹、task key 和结果，变更后重新人工复核。旧 `ip_fit` 只读兼容，不与新对象结果混算；页面、MCP 与 Provider schema 同步兼容测试。缺少 IP 设定、商品约束或视觉证据时，只能输出局限与补证据动作；设定、素材权利或有效期变化后，相关选题和分析标为待复核，不自动继续发布。
3. 决策层由人决定采用、观察或否决；系统记录负责人、截止时间、目标、审批及素材授权。系统不自动发布、不自动调用付费生成模型。
4. 反馈层拟先接非个人汇总数据；自有账号、商家/票务 API 只有在实际授权和**逐字段可用性/口径**核验后才接入。指标按对象目标分组：认知（触达/记忆）、内容（观看/互动）、意向（访问/咨询）、经营（预订/核销/收入）、体验（评价/投诉）。导入状态区分 draft/validated/superseded/retracted，保留来源修正、撤回和重复导入证据；未知值不能填 0，跨平台原始指标不能直接相加。
5. 复盘层在采用决定时冻结主指标、最小样本、观察窗和比较策略，之后记录对照条件、天气/节假日/排期/投流/库存等混杂因素；自然流量与付费流量分开。缺失基线、口径或对照时显示证据不足或不可归因，不把相关性写成因果，也不事后挑选有利指标。被否决和表现不佳的案例也进入经验库。

## 必须先补的权限边界

公开视频的 Canonical 记录可由多个主体引用，但主体设定、未公开剧本、受限素材、审核正文、决策和经营数据不能因此变成全局可见。实现前需定义主体成员、角色、证据密级、继承/冲突规则和撤权后的历史读取；`subject_candidate`、L3、发布与效果数据按主体行级授权。研究台、后台脚本和 MCP 使用同一策略，读操作也记审计。当前视频库和简报仍按全局资产查询，尚无上述隔离，这是发布阻点，而非仅靠前端隐藏即可完成。

## 可复用验收

用至少两个不同类型对象复验同一通用链：一条 IP/演艺对象（首选螭吻九九），一条景区商品或活动对象。两个对象共享采集、证据、任务状态、权限和账本，但各自使用不同的 profile 扩展和成功指标；一条视频可以在一个对象下相关、在另一个对象下无关，简报、评分和 L3 不串项目。设定变化触发重新审核；旧 L3 结果只读，新版在页面和 MCP 下均能正确显示且不会越权。未获授权的剧本/素材不进入 L3、共享 MCP 或普通用户页面；成员撤权后历史受限数据不可继续读取。结果导入在同一来源记录/口径/观察窗下幂等，修订和撤回可追溯。所有状态均能回链原始证据与版本；未发布/无自有结果的卡片明确停在“待验证”，单案例或无反例结果不得自动升格为可复用规则。实际发布与业务结果仍需用户/运营方执行并提供授权数据。

安全边界：完整保密剧本、未授权媒体、Cookie、游客个人订单和 Secret 不进入 GitHub、L3 提示或共享 MCP；评论/转写与经营数据按角色、最小化、脱敏、保留期和访问审计治理。
