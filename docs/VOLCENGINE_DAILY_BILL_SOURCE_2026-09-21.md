## 官方自动同步接口已定位

从该页面“OpenAPI调试”按钮打开的官方入口：

https://api.volcengine.com/api-explorer?action=ListBillDetail&groupName=%E8%B4%A6%E5%8D%95%E4%B8%AD%E5%BF%83&serviceCode=billing&version=2022-01-01

文档确认 `ListBillDetail`、版本 `2022-01-01`、服务 `billing`，支持：

- `BillPeriod=YYYY-MM`，`ExpenseDate=YYYY-MM-DD`。
- `GroupTerm=2` 产品汇总；`GroupPeriod=1` 按天汇总。
- `Product` 为产品标识数组。不能直接假定中文展示名就是 API 标识，须从真实响应核对。
- `IgnoreZero=0` 保留零额行；`NeedRecordNum=1` 返回总数。
- `Limit` 为 1–300；`Offset` 为跳过的记录数，必须分页取全。
- `Warning` 可表示筛选条件被忽略或降级，不能无条件按成功同步处理。
- 响应区分 `PayableAmount`、`PaidAmount`、`UnpaidAmount` 和 `Currency`。按用户每日消费需求展示应付费用时，须明确不是“现金已扣款”。
- 文档标注 5 QPS，完整上月账单通常于次月第 2 个自然日 12 点后获取。

本轮只阅读文档，没有点击“发起调试”。控制台登录不代表服务器已具备账单 OpenAPI 签名凭据或权限。

## 接入边界与下一步

1. 核验既有配置是否有适用的 billing 只读签名凭据；Ark 模型调用 API Key 不得直接当账单签名密钥使用。缺少权限时先提出最小只读授权，不自行扩大权限。
2. 用真实只读响应确认产品标识、金额字段与账期；按天、按产品同步，并标记“账户产品费用”范围，避免误称项目独占消费。
3. 使用十进制定点金额、完整分页、同日快照更新；空列表/错误/筛选警告不能写成零。明确出账延迟与更新时间，保留近期日期回补。
4. 此前模型报价估算继续保留为估算，供应商日账独立展示，不相加造成重复计算。不做用户未要求的逐请求分摊工程。

## 数据契约实现增量

迁移 019 和离线解析器已由 PR #118 合并，主线合并提交为 `ce8ae1c4c3358e0064daee45a0dd35540025a6e6`；尚未发布到测试服务器：

- 日账唯一键增加明确的 `bill_scope_key`。TikHub 沿用账户汇总；火山按 API 返回的 Product code 每个产品一行，中文名称只作显示标签。
- 分开保存应付、已付、未付；`total_cost` 是该声明范围的有符号账单金额，支持退款或调账。缺失调用次数保持 NULL。
- `billing_finality` 只接受 preliminary/final；final 只能由供应商明确事实传入。筛选降级 Warning 独立处理，解析即失败且不覆盖既有有效快照。
- 解析结果必须覆盖全部指定产品、日期和 CNY 币种一致，并要求 `Total` 与已收集列表数量相等；空列表、缺页、产品 code/name 映射歧义均不写零。
- 研究台后端及页面已适配产品范围和三类金额，首页按真实 `billing_finality` 区分“已终账”与“当日累计，未终账”。签名、分页 transport、只读身份及计划尚未实现，Ark/ASR API Key 不参与账单认证。

验证：从旧 schema 写入现有 TikHub USD 0.319 快照后应用迁移 019，金额、请求数和账户范围均保留；另一个一次性 PostgreSQL 运行 37 项费用/首页/运行台测试全部通过，两个临时库均已删除。完整本地测试通过，前端构建及账期显示断言通过。

## 测试服务器发布顺序

不得单独执行迁移 019。当前服务器的 TikHub 同步任务仍锁定旧数据库冲突键，正确顺序为：

1. 暂停 `sync_daily_spend` 计划并记录现有金额、请求数和最后同步时间。
2. 发布锁定 `ce8ae1c4c3358e0064daee45a0dd35540025a6e6` 的新脚本及 Python 3.12 依赖锁；新脚本在新范围字段缺失时会在供应商请求前拒绝执行。
3. 在已完成备份的前提下执行迁移 019，核对既有 TikHub 快照原值未变。
4. 发布研究台应用，手动执行一次 TikHub 同步，对比供应商响应、数据库和页面。
5. 全部一致后重新启用计划；任一步失败时保持计划停用，不写零覆盖最后有效快照。

## 测试服配置盘点

通过 JumpServer 调用既有 Windmill 的变量与资源列表，仅输出匹配项的路径和类型，未读取/输出密钥值。匹配 `volc|ark|asr|bill|access_key` 的变量只有 `ark_api_key`、`asr_worker_config`；匹配火山/账单名称的资源为空。该盘点说明现有命名配置未提供专用 billing 凭据，不推断所有未知命名 Secret 的内容。

已向用户请求专用账单只读身份及测试服 Secret 保存授权，尚未创建身份或改变权限。

现有 `015_supplier_daily_spend.sql` 对余额消费、赠额消费及请求数均有 NOT NULL 约束，并要求费用非负；不能直接塞入火山应付/已付账单，也不能为缺失的请求数编造零。接入需要保留字段语义与缺失状态，并明确退款/调账处理；现有 TikHub 同步行为必须回归验证。

PR #114 之前，首页 `supplierDailySpendFootnote` 把全部记录标为“账户总费用”，且只使用第一条记录的日期/时区。PR #114 先修复逐供应商账期，PR #118 继续完成产品范围、产品标签、空调用次数和终账状态的存储及展示适配。
