# 每日实际费用

内部运行及版本标识的精确定位保存在受控记录。

用户验收口径：知道每天花多少钱即可，不逐笔对账、不按任务分摊。

## 数据与页面

TikHub 免费接口 `GET /api/v1/tikhub/user/get_user_daily_usage` 已通过已登录后台验证。
真实字段是 `data.date`、`usage`、`balance_usage`、`free_credit_usage`、
`total_request_per_day`、`paid_request_per_day`，时区来自顶层 `time_zone`。
`total_request_per_day` 不可简写成并不存在的 `total` 字段。

同步脚本只保留账户标签、日期、币种、金额、请求数和获取时间，不存邮箱或原始响应。
金额从供应商返回读取并规范浮点尾数，不用本地请求次数乘单价。
失败不写零、不覆盖上次成功快照；相同日期较旧的获取结果不能覆盖较新的结果。

首页展示供应商当日累计；运行台提供每日列表。金额为**整个供应商账户**口径，
不随页面的平台筛选变化。USD 与 CNY 不合并，尚未接入的供应商不显示虚构的 0。
TikHub 按 `America/Los_Angeles` 账期判断当日，不按北京时间切日。
实时同步只接受响应所报时区的当前日期；供应商本地午夜后经过的前两小时内允许前一日的收尾快照（夏令时回拨也不延长窗口），但任务状态明确标为 `rollover_previous_day`，不算当前日已同步。更早账期或未来账期均拒绝且不写库，避免旧数据让定时任务虚报完成。

## 同步方式

`f/content_research/collectors/sync_daily_spend` 是服务端脚本：读取既有 TikHub Secret、
使用既有研究数据库资源，不依赖浏览器登录。计划每小时执行一次；单次免费 GET、零重试，
超过两小时未成功获取的当前账期数据提示可能过期。查询失败可以下一周期继续，不重新采集视频。

先应用迁移 `015_supplier_daily_spend.sql`；再部署固定 Git SHA 的同步脚本和页面。
定时任务参数：`db=$res:f/content_research/research_db`、`account_scope=default`。
部署阶段必须检查既有同路径计划，更新而非创建重复计划，并手动执行一次核对数据库与页面。

## 边界

目前该接口没有历史日期参数。历史行是当时最后获取的累计快照，不是已终账账单；
例如最后一次同步之后、供应商午夜之前的消费不能凭空补出。
页面明确标“历史末次累计（未终账）”；需要精确历史终账时从后台 CSV／JSON 补充，
不把快照冒充最终结算。本次优先满足查看当日实际累计的业务需要。

阿里、火山的日账接入需要各自账单来源与权限，不从 token 或音频估算冒充实际扣款。
本文记录实现契约；是否已部署、定时任务是否已运行，以独立部署验收记录为准。
