# V1 技术架构

## 1. 范围

V1 聚焦：

- 外部抖音数据采集
- 黑马/热点粗筛
- 重点样本逐级精研
- 历史数据与指标快照
- Web 研究台
- 搜索与筛选
- Codex MCP 访问
- 成本与任务运行可观测

暂缓：

- NAS 视频资产归档
- LibTV 自动生产
- 发布后账号表现自动回流
- 独立前端项目
- 独立 MCP Server
- 自研抖音爬虫

## 2. 组件

### TikHub

作为 V1 主数据源，但仅通过 Provider 适配层访问。

### Windmill

承担：

- 定时任务
- Python/Go/SQL 脚本运行
- Flow 编排
- Secrets
- 重试与运行历史
- 内部 App
- MCP Gateway

### PostgreSQL

作为唯一事实数据库。大文件不进入数据库。

## 3. 分层漏斗

### L0：全量采集

只拉基础元数据和榜单发现信息，不调用 LLM。

### L1：代码粗筛

只使用 SQL / Python / Go：

- 去重
- 低粉高表现
- 增长速度
- 账号基线偏离
- 新鲜度
- 多榜单命中
- 关键词/赛道规则
- 异常值

### L2：轻量研究

按需补：

- 少量评论
- Transcript / ASR
- 关键词
- 相似度
- 聚类

默认仍不使用强模型。

### L3：深度研究

只对少量高价值 Case 使用 LLM：

- Hook / 叙事结构理解
- 评论语义理解
- 多案例比较
- 机制假设
- IP 适配
- Pattern 候选

## 4. 调用决策

执行任务前按顺序判断：

1. SQL 能否解决？
2. 普通代码能否解决？
3. 规则/统计能否解决？
4. Embedding/聚类能否解决？
5. 均不能解决时才调用 LLM。

## 5. 数据治理

必须保留：

- 平台唯一 ID
- 原始 JSON
- 发现来源
- 采集时间
- 指标快照
- 规则版本
- 分析版本
- 模型与 Prompt 版本
- 人工修改记录
- API / ASR / LLM 成本

禁止将缺失指标写成 0。

## 6. 搜索

V1：

- 精确字段
- ILIKE
- 标签过滤
- 时间过滤
- 账号/视频联合检索

数据规模与使用需求达到阈值后再评估 PGroonga / pgvector / 独立搜索引擎。

## 7. V1 Web 研究台

至少包括：

- 今日发现
- 黑马视频
- 对标账号
- 历史案例
- 搜索
- Case 详情
- 指标时间线
- 收藏/专题
- 人工标记
- 任务与成本概览

## 8. MCP 原则

Codex 默认读取 PostgreSQL 中已经缓存和治理的数据。

外部付费接口调用必须通过 Windmill 工具显式触发，并经过预算/缓存规则。
