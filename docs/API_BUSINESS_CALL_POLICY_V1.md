## 结论与证据范围

当前“所有视频立即补 50 条批量详情”的规则不适合小样本，也不适合高频增长监测。
推荐改为：低价榜单发现 → 本地去重和初筛 → 按所缺字段选择详情或统计 →
重点样本补评论/转写 → 有证据的案例进入 L3。路由同时比较费用、字段覆盖率、
新鲜度和截止时间，不把批量、缓存、低单价自动等同于性价比。

本次从官方公开价格接口取得 1460 条价格记录，从当前在线 OpenAPI 取得 1048 个路径；
按现有蓝图、接口目录及可替代方案筛选 116 个候选/费用接口。115 个有价格记录，
116 个有请求契约。完整逐项表见 [接口价格与输入表](pricing/tikhub-20260920.md)，
类型、必填参数、默认值、枚举与约束见 [机器可读清单](pricing/tikhub-20260920.json)。
这是报价和契约核验；不代表 116 个接口都已启用或逐个做过付费数据验收。

本次研究只读取公开报价/文档和已登录后台，没有新增付费数据、ASR 或模型请求。
既有真实采集证据仍为低粉榜 1 次 + 批量详情 1 次，共 USD 0.051。

### 证据优先级

1. 指定账号逐接口账单：证明已经发生的实际扣费。
2. `get_all_endpoints_info` / `get_endpoint_info`：当前单价、折扣资格、免费额度资格、限速。
3. 当前在线 OpenAPI：方法、参数、分页、批容量和数据用途。
4. 网页说明/旧 SDK/旧文档：作为参考，冲突单独登记。

不能从通用 `calculate_price` 返回的基础费率推断所有 endpoint 的单价，
也不能把我们自己的 `actual_cost` 列名当作已经取得供应商实际账单。

### 基础价下的路由公式（待部署；先验证同样本字段等价性）

先查询每个视频的字段新鲜度，去掉不需要刷新的ID，再按稳定ID排序。
`N` 为剩余有效去重ID数；N=0时不外呼。

- 完整详情：`floor(N/50)` 个50批 + 余数中 `floor(r/10)` 个10批 + 最后不足10条逐条获取。
  基础费用合计 `N × 0.001`，满批以更少请求完成相同内容；3条详情为0.003。
- 统计：`floor(N/50)` 个50批 + 余数以每2条一组调用普通统计。
  费用 `floor(N/50) × 0.025 + ceil((N mod 50)/2) × 0.001`。
  余数49也可用50批，两种都是0.025，优先更少请求。
- 有折扣时重新比较：50详情批有效单价为 `0.050 × (1-d)`，单详情不支持折扣。
  一批与N个单详情等价点为 `N=50×(1-d)`；10%档为45条、20%档为40条、50%档为25条。
  还需比较10条批的组合；每档只是该请求的边际价格，不把折扣套到全天所有请求。
- 遵循截止时间：低延迟的人工详情用单条；后台到期快照可在短窗口汇合。
  不能为凑50条把一个新热点无限拖延。

| 所需视频数 | 强制50详情批 | 基础价详情组合 | 强制50统计批 | 统计组合 |
| ---: | ---: | ---: | ---: | ---: |
| 3 | 0.050 | 0.003 | 0.025 | 0.002 |
| 10 | 0.050 | 0.010 | 0.025 | 0.005 |
| 25 | 0.050 | 0.025 | 0.025 | 0.013 |
| 50 | 0.050 | 0.050 | 0.025 | 0.025 |
| 51 | 0.100 | 0.051 | 0.050 | 0.026 |
| 1000 | 1.000 | 1.000 | 0.500 | 0.500 |

以上都是报价算例，不是已发生的新费用。3条样本的完整采集在字段同样可用时，
“榜单0.001 + 3条详情0.003”预计共0.004，相比既有0.051少0.047（约92.2%）；
若只需统计则预计0.003，但输出内容不同，不能称为等价替代。

### 新鲜度与缓存

当前代码只有整个请求指纹缓存，批次中的顺序/成员变化会失配；不是逐视频缓存。
建议新建“字段级新鲜度 → 待刷新集合 → 批次规划”，再落入现有请求缓存：

- 视频内容/作者关系：首次补全，非必要不重复；失效媒体URL按需求刷新。
- 高分且发布0–6h：统计1h；6–24h：2–3h；1–3d：6–12h；3–7d：24h；之后退出活跃池。
- 普通候选：按新快照/榜单增量再评分，不全库小时轮询。
- 榜单/搜索不同来源相同视频：保留发现来源，不重复拉一次完整详情。
- 缓存返回不能伪造新观测时刻，否则会污染增长速度。

### ASR 的钱按时长算，HTTP请求数单独计

服务地址 `https://openspeech.bytedance.com`，新控制台使用 `X-Api-Key`。
同一任务1次submit + k次query是 `1+k` 次HTTP交互，按时长服务的报价模型只计算
该任务音频时长一次。官方计费说明按毫秒累加后折算小时，双声道按音频时长计。
独立query没有列出单次单价；正式账单对账前，轮询费用是否无独立扣款仍记为待账单核验。
任务未完成时继续查同一任务，不因排队重新submit。

- 60秒约 ¥0.013333；100条60秒约 ¥1.333333，500条约 ¥6.666667。
- 旧大模型标准版 ¥2.3/h、极速版 ¥4.5/h、闲时版 ¥1.2/h；这些不是2.0的费率。
  闲时版也比2.0当前标准价高，因此不能仅凭“闲时”就选择它。

## 6. 计价、对账与性价比指标

TikHub阶梯按账号每日请求量边际累进，只有允许折扣的端点享受：前1000基础价，
之后到5000/10000/20000/30000分别10%/20%/30%/40%，更高50%。
实际边界与跨接口累计顺序应使用账户账单/报价校正；重置日以供应商时区为准，
不要按本机午夜硬拼接。`get_user_daily_usage`、价表、阶梯、计算器均为免费元数据接口，
多数限速1 RPS；数据接口通常10 RPS。TikHub限速按endpoint，不是整个账号共用一个10 RPS桶；
双worker访问同一路径须共享该路径的桶，不同路径可并行。建议桶键为供应商+凭据身份+endpoint。
某些价表rate_limit只写`10`而无时间单位，保留原值，不能自动解析为10 RPS。

用户当前要求取消金额硬上限、清楚记账。因此采用金额观测与明确任务规模；
以下频率和分页是调用质量/效率策略，不能变相恢复80%/95%金额熔断。
供应商余额、限速和接口容量仍需正常处理。

项目至少区分：逻辑任务数、实际HTTP尝试数、供应商计费请求数、原始条数、
有效条数、去重新增数、字段覆盖率、延迟、缓存命中数、估算费用、已对账实际费用。

- 有效成本 = 任务总实际费用 / 有效且新增（或确需刷新的）对象数；分母0单独记为无有效结果。
- 接口选择先满足字段和时效，再比较预期总费用；考虑空结果、重试/替代路线的额外费用。
- TikHub官方说明非200请求不收费；网络超时无法据此判断上游是否已成功计费，暂记unknown。
  返回200但只有重复/无用数据仍不能假定免费。
- 当前手动采集关闭自动重试；普通Transport默认可重试3次。后续自动任务要记录每次尝试，
  429做限速退避；未知结果先查记录，不由App、Flow、SDK三层叠加重试。
- 当前TikHub成功调用的费用通常来自单价快照估算。只有来源为账户账单的记录叫“已对账”。
  `daily_budget.spent_cost`当前是预占计数，不能把它当供应商自动结算。
- USD与CNY分列；如需要合计人民币，另记录汇率和日期，不直接相加。

建议每日同步一次价格快照并比较变动；新启用接口前读取报价；每日账单按endpoint、币种、
时间窗对账，超时未知项单列。不需要在每次抓数据前再查一次价格。
研究台读库/翻页默认不触发外部刷新，明确点击刷新才创建采集任务。
